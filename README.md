# EventLoop

Подбор мероприятий по Пушкинской карте в формате свайпов.

Работа поделена надвое. **Бот в MAX** спрашивает сколько всего на карте, сколько
из этого на кино и откуда считать расстояние (геолокация, точка Москвы или Казани
кнопкой, «Пропустить») — и присылает кнопку, которая открывает мини-приложение
и передаёт ему оба кошелька и точку отсчёта.
**Мини-приложение** делает всё остальное: карточки, свайпы, фильтры по дате,
категории и расстоянию, избранное, подтверждение покупки и подсчёт остатка.

Листать карточки в переписке медленнее, а две реализации одной ленты расходятся
на второй же правке — поэтому лента живёт только в приложении.

## Бот

**https://max.ru/t560_hakaton_max_bot** — «Хакатон МАХ 560», `@t560_hakaton_max_bot`

Имя и ссылку приложение печатает в лог при каждом старте:

```
Связь с MAX есть. Бот: «Хакатон МАХ 560», username: @t560_hakaton_max_bot, id: 387017712
Открыть диалог: https://max.ru/t560_hakaton_max_bot
```

Если вместо этого в логе ошибка — токен отозван или недействителен.

## Запуск

Нужен только Docker. Java, Maven и PostgreSQL ставить не надо — всё собирается
внутри образа.

```bash
docker compose up --build
```

Токен бота лежит в `.env` рядом с `compose.yaml` и подхватывается автоматически,
поэтому команда одна. Если `.env` потерялся, compose остановится с подсказкой,
а не поднимет молча неработающего бота: скопируйте `.env.example` в `.env`
и впишите `MAX_BOT_TOKEN`.

Первая сборка занимает несколько минут — Maven тянет зависимости. Одна команда
поднимает приложение и PostgreSQL. Схема, площадки, станции метро и афиша
из 163 мероприятий приезжают миграциями Flyway при старте: отдельных шагов нет,
интернет для наполнения базы не нужен.

Остановить: `docker compose down`. Стереть и данные: `docker compose down -v`.

## Статистика для защиты

Статистика — экран мини-приложения, и видят его только администраторы.

**Кто администратор.** MAX user id через запятую в `ADMIN_MAX_IDS` в `.env`
(например, `ADMIN_MAX_IDS=12345678,87654321`). Пусто — статистику не видит никто.
После правки `.env` выполните `docker compose up -d` — compose пересоздаст `app`
с новым списком.

**Как узнать свой id.** Напишите боту `/stats`. Не администратору бот отвечает
«Такой команды нет.» — ни роли, ни id чужим не раскрываются. Сам id пишется
в лог сервера: `docker compose logs app | grep "/stats от не администратора"` —
это число и вписывается в `.env`.

**Как открыть.** Администратор пишет боту `/stats` и получает кнопку «Открыть
статистику». Мини-приложение открывается сразу на экране статистики с метриками
пилота (их список — ниже, в «Метриках пилота»). Обновляется раз в 3 секунды,
пока экран открыт. Команда скрытая: в меню бота её нет, состояние разговора она
не меняет.

Эндпоинты:

- `GET /api/me/reactions` — отметки пользователя; без валидного `X-Init-Data` — 401.
- `POST /api/actions` — действие из приложения (`VIEW`, `LIKE`, `SAVE`, `DISLIKE`, `UNDO`, `CLICK_BUY`, `PURCHASE_YES`, `PURCHASE_NO`, `PURCHASE_CANCEL`); 204, без подписи — 401.
  Тело — `{ eventId, action, priceRub, category, city }`. `city` необязателен:
  `moscow` или `kazan`, другое значение — 400. Действия без города (записанные
  до обновления) в разбивке по городам идут в графу «Не указан».
- `GET /api/stats` — агрегаты без id пользователей, только с валидным `X-Init-Data`
  администратора: без подписи или с битой — 401, не администратор — 403.

```bash
curl -i http://localhost:8080/api/stats   # без подписи initData — 401
```

**Как включить синхронизацию из MAX.** Бэкенд должен быть доступен по HTTPS:
на VPS — через reverse proxy, на ноутбуке — туннелем, например
`cloudflared tunnel --url http://localhost:8080`. Дальше один из двух путей:

- адрес мини-приложения в @MasterBot указать на `<бэкенд>/app/` — приложение и
  API на одном адресе, CORS не нужен (основной вариант);
- в копии на GitHub Pages прописать адрес бэкенда в `<meta name="eventloop-api">`
  в `index.html`, а origin Pages держать в `MINIAPP_ORIGINS` (по умолчанию
  `https://skaytskayt.github.io`).

### Метрики пилота

Экран отвечает на один вопрос: помогает ли бот быстро найти мероприятие и
купить на него билет.

| Метрика | Что показывает | Как считается |
|---|---|---|
| Свайпов до выбора | Как быстро человек находит «своё» в ленте | Медиана по людям: сколько карточек он просмотрел до первого «Пойду». Считаются только те, кто хоть раз отметил «Пойду» |
| ₽ доведено до покупки | Сколько денег с Пушкинской карты бот довёл до реальных билетов | Сумма цен купленных билетов; под ней — средний чек и число билетов |
| Из «Пойду» в покупку | Насколько отметки «Пойду» превращаются в покупки | Доля пар «человек — мероприятие» с «Пойду», по которым билет сейчас куплен |
| Активны | Живой ли продукт прямо сейчас | Уникальные люди сегодня / за 7 дней (сегодня и 6 предыдущих) и сколько из них пришли сегодня впервые |
| Воронка по людям | Где люди отваливаются | Открыли приложение → отметили «Пойду» → перешли к покупке → купили билет; % — от открывших |
| Время до покупки | Сколько занимает путь от первого касания до билета | Медиана минут от первого действия человека до его первой подтверждённой покупки |
| Вернулись | Возвращаются ли к боту | Доля людей, заходивших в 2 и более разных дня |
| Карточек на человека | Насколько глубоко листают ленту | Среднее число просмотров карточек на человека |
| Топ-5 мероприятий | Что цепляет сильнее всего | Рейтинг: число «Пойду» плюс покупки с двойным весом; рядом — «Пойду» и куплено |
| Категории | Какие направления нравятся, а какие отвергают | «Пойду» по категории и доля «не нравится» среди оценок |
| Москва / Казань | Как пилот идёт в каждом городе | Люди, «Пойду», покупки и рубли по городу |

Покупки везде — подтверждённые и не отменённые; сутки — по московскому времени;
id пользователей в ответ сервера не попадают. Нет данных для метрики — экран
пишет «пока нет данных», а не 0 %.

### Демо-данные для статистики

Чтобы экран не был пустым на защите, `tools/demo/seed-stats.mjs` шлёт через
`POST /api/actions` правдоподобные действия ~20 выдуманных пользователей по
настоящей афише из `data.js`: просмотры, «Пойду», «в желаемое», «не нравится»,
переходы к покупке, покупки и отмены. initData подписывается токеном бота —
так же, как это делает MAX. Нужен Node 18+, `npm install` не нужен.

```bash
TOKEN=<токен бота> node tools/demo/seed-stats.mjs            # bash
$env:TOKEN='<токен бота>'; node tools/demo/seed-stats.mjs    # PowerShell
```

`TOKEN` — тот же, что `MAX_BOT_TOKEN` в `.env`. Остальные переменные:
`BASE` — адрес сервера (по умолчанию `http://127.0.0.1:8080`), `USERS` — сколько
пользователей (1..99, по умолчанию 20), `SEED` — зерно сценария (тот же SEED —
те же действия), `DRY_RUN=1` — ничего не отправлять, только показать план.
Демо-пользователи получают id **990100–990199**.

Ограничение: `created_at` ставит сервер, задним числом записать нельзя, поэтому
все демо-действия — «сегодня». Для них «Вернулись» — 0 %, «Время до покупки» —
меньше минуты, «Активны» сегодня = за 7 дней. Повторный запуск дописывает журнал.

Удалить демо-данные:

```bash
docker compose exec db psql -U eventloop -d eventloop -c "DELETE FROM miniapp_action WHERE max_user_id BETWEEN 990100 AND 990199; DELETE FROM miniapp_reaction WHERE max_user_id BETWEEN 990100 AND 990199;"
```

### Требования

Только Docker. Java и Maven локально не нужны — сборка идёт внутри образа.
Для запуска без контейнера понадобится **JDK 21** и PostgreSQL 17.

### Токен

Токен берётся **только** из переменной окружения `MAX_BOT_TOKEN`, в исходном коде
его нет. `.env` в `.gitignore`, в git и в образ не попадает — в поставку решения
кладётся отдельным файлом.

Получить токен можно в личном кабинете MAX для партнёров. Учтите два
организационных ограничения: бот создаётся только при верифицированном профиле
организации, ИП или самозанятого, а пользователи получают к нему доступ
**после прохождения модерации** — это срок, который стоит заложить заранее.

### Как компоненты связаны

```
MAX ──long polling──> MaxGateway ──> DialogRouter ──> PostgreSQL (состояние диалога)
                                          │
                                          └──кнопка с балансом──> Mini App (/app/ или GitHub Pages)
                                                                        │
                                                                        ├──> билетный оператор
                                                                        │
                                                                        └──/api (X-Init-Data)──> MiniAppController ──> PostgreSQL
```

**Бот и приложение связаны ровно одним контрактом** — параметром запуска.
Бот присылает кнопку `open_app`, которая открывает мини-приложение бота внутри
MAX, и кладёт в её `payload` оба кошелька: `2000_3000` (кино_остальное; MAX
пропускает в payload только латиницу, цифры, `_` и `-`). Приложение получает
его через мост MAX в `WebApp.initDataUnsafe.start_param`, читает суммы как
остаток на текущий момент и проверяет как чужой ввод: нечисловое, отрицательное
или больше номинала кошелька значение игнорируется. Прямая ссылка
`?cinema=2000&other=3000` тоже понимается.

С точкой отсчёта payload четырёхчастный: `2000_3000_557961_491064` — широта и
долгота, умноженные на 10000, целыми со знаком (не длиннее 64 символов).
Приложение понимает оба вида: без координат считает от центра Москвы.
Названия точек оно знает из своего списка `ORIGINS`, продублированного из
`Screens.ORIGINS`, — синхронность проверяет `ScreensMiniAppTest`.

Кнопке нужен username бота — переменная `MAX_BOT_USERNAME`; не задана — бот
отвечает текстом без кнопки и пишет об этом в лог, а не молчит. Адрес самого
приложения (GitHub Pages) привязан к боту в @MasterBot. Кнопка мини-приложения
в меню бота открывает его без суммы — тогда приложение считает от номинала.

### Решения, которые стоит знать до правок

**Бот спрашивает только баланс и точку отсчёта:** сначала сколько всего на карте,
потом сколько из этого на кино. Остальное — разница, и она должна влезть в свой кошелёк:
при 5000 ₽ на карте на кино может быть только 2000 ₽. Третий вопрос — откуда
считать расстояние: геолокация (её умеет запросить только бот), одна из восьми
точек кнопкой или «Пропустить». Точка хранится в `app_user.origin_*` и
меняется в любой момент — старые кнопки в чате остаются живыми. Всё остальное —
в приложении. Команда одна, `/start`; меню, фильтры и кнопки под карточками из
бота убраны.

**Состояние диалога — в PostgreSQL.** Строка в `app_user` создаётся при первом
сообщении, поэтому перезапуск контейнера не сбрасывает разговор на середине.

**Состояние ленты — на сервере, когда приложение открыто из MAX.** Лайки,
отложенное, дизлайки и покупки хранятся в `miniapp_reaction` под MAX user id,
который сервер берёт из подписанного `WebApp.initData` (заголовок `X-Init-Data`,
подпись проверяется токеном бота). `localStorage` — кеш и режим без MAX: по
прямой ссылке приложение не делает ни одного запроса к `/api`. Фильтры и
кошельки остаются в браузере.

**Лента подстраивается под вкус.** Неоценённые карточки сортируются по сходству
с отмеченными: та же категория — 3, та же площадка — 2, цена в пределах ±30 % — 1,
расстояние в пределах ±2 км — 1. «Пойду» и покупка дают вес 1, отложенное 0,5,
дизлайк −1. Без истории порядок исходный. Над карточкой с положительным счётом
написано, на что она похожа: «Потому что тебе понравилось «…»».

**Схема описывает только то, что работает.** Таблицы под серверные реакции
и покупки убраны миграцией `V6`: пустые таблицы обещали синхронизацию, которой
в MVP нет. `V8` вернул таблицы вместе с кодом, который в них пишет.

## Тесты

```bash
./mvnw test
```

176 тестов, все проходят (живая проверка ссылок без флага пропускается). Заметная часть проверяет **сами данные**, а не код:
координаты площадок, наличие файла афиши у каждой карточки, уникальность
идентификаторов, цену в пределах кошелька и то, что ссылка ведёт на страницу
мероприятия, а не на поиск. Опечатка в пути к афише не падает исключением — она
даёт пустой прямоугольник, который заметишь, только долистав до него.

Живая проверка ссылок требует сети и вынесена под флаг — прогоняйте перед показом:

```bash
./mvnw test -Dlinkcheck=true -Dtest=SeedLinkCheckTest
```

## Данные

Два набора, и это важно понимать до показа.

**База.** `R__seed_z_events.sql` — 163 мероприятия, снятые импортом со страниц
Пушкинской карты билетного оператора ticketland.ru: настоящие названия, даты,
цены, ссылки и афиши. Площадки, адреса и координаты настоящие (координаты
приблизительные, ±150 м). Станции метро — 347 штук из OpenStreetMap.
Сид зафиксирован в миграции, чтобы `docker compose up` давал работающее демо
без сети: у источника антибот-защита, и на чужой машине запрос может не пройти.
Свежую афишу подтягивает `POST /admin/import` — он обновит те же строки
по `external_key`.

**Mini App.** `static/app/data.js` — снимок от 21 октября 2026: 160 мероприятий,
по 80 в Москве (25 площадок) и в Казани (7 площадок), и 160 локальных афиш.
Только будущие на момент сборки сеансы: в Москве с 21 октября по 31 декабря,
в Казани с 21 октября по 29 ноября. Отдельный набор, потому что за лентой
приложение на сервер не ходит (см. «Ограничения»).

Снимок собирает скрипт, руками `data.js` не правится:

```bash
node tools/feed/build-feed.mjs
```

Нужны node 18+ и сеть, `npm install` не нужен. Скрипт обходит раздел Пушкинской
карты на `www.ticketland.ru` и `kzn.ticketland.ru`, читает JSON-LD, отбрасывает
прошедшие сеансы и билеты дороже кошелька, скачивает новые афиши, удаляет
ненужные и пересобирает `data.js` и `CREDITS.md`. Рядом лежат два реестра —
их коммитят вместе со снимком:

- `tools/feed/venues.json` — координаты площадок. Новую площадку скрипт ищет
  в Nominatim; не нашёл — печатает список и выходит с кодом 1. Тогда впишите
  координаты вручную (`"source": "manual"`) или пометьте `{"skip": true, "reason": "…"}`
  (так помечены гастроли вне Казани и площадки без адреса) и перезапустите.
- `tools/feed/ids.json` — `ticketUrl → eventId`, только дополняется: по `eventId`
  сервер хранит реакции, поэтому id события между снимками не меняется.

Скрипт вежлив к источникам: пауза 1,2 с между страницами листинга, не чаще
одного запроса в секунду к Nominatim со своим User-Agent, известные площадки
повторно не геокодируются. Лимит — 80 событий на город, отбор по кругу между
площадками: копия приложения лежит и в git, и на GitHub Pages, а афиша весит
около 37 КБ; для ленты свайпов этого с запасом, и одна филармония не занимает
всю колоду.
Афиши скачаны со страниц оператора, права принадлежат организаторам,
подробности и ссылки на оригиналы — в `static/app/assets/events/CREDITS.md`.
Перед публичным запуском их нужно либо отдавать по ссылке на лету, либо
согласовать с правообладателями.

## Ограничения

Что осознанно не сделано в MVP:

- **Лента работает на собственном датасете приложения, а не на базе.** За лентой
  Mini App на сервер не ходит: 160 мероприятий зашиты в `data.js`, на сервер уходят
  только реакции. База хранит состояние диалога бота, реакции и служит приёмником
  импорта. Связать ленту с базой — отдельная работа: нужен эндпоинт ленты и
  фильтры на сервере.
- **По прямой ссылке без MAX отметки живут только в браузере.** Подписанного
  initData там нет, поэтому другое устройство их не увидит, а очистка данных
  сайта стирает.
- **Статистика демонстрационная.** Цена и категория приходят в журнал от клиента
  и сервером не сверяются — ленту `data.js` сервер не знает. Свежесть initData
  (`auth_date`) не проверяется, чтобы долго открытое приложение не получало 401
  посреди показа.
- **Расстояние — по прямой от точки из бота**, а не по маршруту. Без точки —
  от центра Москвы; геолокация дальше 100 км от обоих городов заменяется центром
  ближайшего, иначе лента была бы пустой при любом фильтре.
- **Даты сеансов — с 21 октября по 31 декабря 2026** (Казань — по 29 ноября).
  Прошедшие лента скрывает, так что снимок нужно пересобирать
  `node tools/feed/build-feed.mjs`.
- **Два города только в Mini App.** Приложение знает Москву и Казань; база,
  метро и `POST /admin/import` — только московские, проверка координат в схеме
  это закрепляет.
- **Диалог бота ведётся на русском** и не локализован.
- **Импорт закрыт токеном и запускается руками.** Расписания нет.

## Переключение на webhook

Long polling выбран, чтобы демо поднималось на ноутбуке без публичного адреса.
Для production переключение — смена `MAX_BOT_MODE` на `webhook` и заполнение
`MAX_WEBHOOK_URL` и `MAX_WEBHOOK_SECRET`. Требуется HTTPS на 443 и сертификат
доверенного УЦ, самоподписанные MAX не принимает. Код `DialogRouter`
при этом не меняется.

## Что проверено, а что нет

`docs/max-api-facts.md` — построчно: какие возможности API подтверждены
документацией, какие проверены живым запуском, а какие ещё нет.

Проверено: сборка и старт в Docker с чистыми томами, применение всех миграций,
наполнение базы, `/actuator/health`, TLS-соединение с `platform-api2.max.ru`
из контейнера, отказ при отсутствии токена, 106 юнит-тестов и ручной прогон
основного сценария с телефона.

Не проверялось: поведение под нагрузкой, несколько одновременных пользователей,
webhook-режим, работа после 31 декабря 2026.

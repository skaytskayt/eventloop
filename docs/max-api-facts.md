# MAX Bot API: что проверено, а что нет

Документ существует, чтобы никто не проектировал UX под возможности, которых нет,
и не изобретал обходы для тех, что есть.

**Статус: проверено по документации и по содержимому SDK. Живой прогон против
`platform-api2.max.ru` НЕ выполнялся** — нужен действующий токен и бот, прошедший
модерацию. Строки со статусом «не проверено вживую» закрываются первым запуском.

## Платформа

| Факт | Статус | Источник |
|---|---|---|
| Домен API — `platform-api2.max.ru` | подтверждено | офиц. документация |
| Токен только в заголовке `Authorization`, query-параметр не поддерживается | подтверждено | офиц. документация |
| Нужен корневой сертификат Минцифры | подтверждено | офиц. документация |
| Лимит 30 rps на домен | подтверждено | офиц. документация |
| Лимит 2 операции/сек на один чат | **НЕ подтверждено** | только README SDK; в офиц. тексте числа нет |
| Webhook и long polling взаимоисключающи | подтверждено | «Использовать одновременно оба типа нельзя» |
| Long polling не для production | подтверждено | офиц. рекомендация |
| Webhook требует HTTPS на 443 и сертификат доверенного УЦ | подтверждено | самоподписанные запрещены с 25.05.2026 |

**Организационное ограничение, которое не про код:** бота можно создать только
с верифицированным профилем организации, ИП или самозанятого, а пользователи
получают доступ **после успешной модерации**. Это срок, а не строчка кода —
запускать модерацию нужно заранее.

## Возможности, на которых держится продукт

| Возможность | Статус | Как используем |
|---|---|---|
| Изображение по прямому URL, без `POST /uploads` | подтверждено документацией | `poster_url` из датасета уходит в `image.payload.url` |
| Изображение + одно вложение с кнопками в одном сообщении | подтверждено документацией | карточка ленты |
| `POST /answers` с телом `message` заменяет сообщение | подтверждено сигнатурой SDK | один вызов на свайп вместо двух |
| Визуальная перерисовка **картинки** при замене | **не проверено вживую** | см. план Б ниже |
| `PUT /messages` — правка сообщения | подтверждено | запасной путь |
| `bot_started` несёт `payload` из диплинка (до 128 символов) | подтверждено документацией | логируется в `DialogRouter.onStart` |
| Клавиатура: до 210 кнопок, 30 рядов, до 7 в ряду (до 3 для `link`) | подтверждено | у нас максимум 3 в ряду |
| Длина `url` кнопки — до 2048 символов | подтверждено | ссылки датасета короче |
| Предельная длина `payload` callback-кнопки | **не документирована** | держим ≤64 байт, тест `CallbacksTest` следит |
| MAX отвечает HTTP 200 и при неуспехе, ошибка в теле | подтверждено | `MaxGateway` логирует `success == false` |

### План Б, если картинка не перерисовывается

Документация разрешает замену вложений, но поведение клиента извне проверить нельзя.
Если при `POST /answers` афиша не обновляется визуально:

1. `DELETE /messages` для старой карточки, затем `POST /messages` с новой — два вызова
   вместо одного, упирается в лимит частоты, но работает гарантированно.
2. Крайний вариант: текстовая карточка без афиши. Продукт остаётся рабочим,
   теряется только внешний вид.

Точка изменения — один метод `MaxGateway.replaceOnCallback`. Остальной код не затрагивается.

## Что везёт SDK

`ru.etsft.max:max-bot-api-*:0.5.0`, Apache-2.0, Maven Central.

- Собран против Spring Boot **4.1.1** и Jackson **3.1.5** — ровно наши версии
  (проверено по `gradle/libs.versions.toml` в репозитории `etsft/max-bot-api-java`).
- Байткод Java 21.
- Везёт с собой сертификаты Минцифры — своему клиенту их пришлось бы добавлять
  в trust store образа вручную.
- Типы отправляются корректные: `image`, `inline_keyboard`, `callback`, `link`
  (проверено дизассемблированием методов `type()`).

**Подводный камень упаковки:** POM модуля `max-bot-api-spring-boot` не объявляет
зависимостей на Spring, хотя компилируется против него. Maven поэтому не проверит
совместимость версий — несовместимость проявилась бы только при старте контекста.

**Не использовать** `max-messenger-client/max-bot-api-client-java` — несмотря на 178★,
это `ru.max:max-bot-api:0.0.6-SNAPSHOT`, Java 1.8, Jackson 2, без Spring,
в Maven Central отсутствует.

## Свойства конфигурации

Извлечены из `spring-configuration-metadata.json` внутри jar — это фактические имена.

```properties
max.bot.mode                        # longpolling | webhook. БЕЗ НЕГО НИЧЕГО НЕ ЗАПУСТИТСЯ,
                                    # причём без единой ошибки в логе
max.bot.longpolling.token
max.bot.longpolling.poll-timeout    # по умолчанию 30 секунд
max.bot.longpolling.update-types
max.bot.webhook.token
max.bot.webhook.url
max.bot.webhook.path                # по умолчанию /max-bot/webhook
max.bot.webhook.secret              # заголовок X-Max-Bot-Api-Secret
max.bot.webhook.auto-register       # по умолчанию true
max.bot.webhook.async-dispatch
```

Из описания `async-dispatch` следует важное: **MAX считает ответ дольше 30 секунд
неудачной доставкой и присылает обновление повторно.** Дубли — документированное
поведение платформы, поэтому идемпотентность обязательна. У нас её обеспечивают
уникальные индексы `reaction_unique_per_event` и `purchase_unique_per_session`.

## Чек-лист первого живого запуска

- [ ] Токен перевыпущен (старый засветился в переписке)
- [ ] `GET /me` отвечает **из контейнера**, а не только с хоста — это проверка сертификата
- [ ] `/start` в живом клиенте возвращает приветствие
- [ ] Карточка приходит с афишей и кнопками под ней
- [ ] Нажатие кнопки **заменяет** сообщение, а не добавляет новое
- [ ] Афиша при замене визуально обновляется → если нет, включаем план Б
- [ ] Заведомо битый запрос виден в логах как ERROR с текстом из тела ответа
- [ ] `GET /subscriptions` пуст при работе через long polling
